# Engineering architecture

## Scope & quality gates

- Platform: iOS 17+ (primary verification target iOS 27.0.1), SwiftUI, guest IPA for LiveContainer; code editing from Windows 11.
- Xcode project is generated by deterministic `tools/generate_xcodeproj.py`; no XcodeGen, CocoaPods, hosted backend or Apple developer account is required for compiling an **unsigned** device IPA.
- Build and runtime are separate acceptance criteria. GitHub Actions (`xcode-27`) compiles arm64 device code; only testing on the actual iPhone validates LiveContainer compatibility.
- Swift Package core compiled/tested on Linux/Windows-compatible Swift where possible. Apple UI and system service code compile on a GitHub-hosted macOS arm64 runner.

## Module boundaries

```
Sources/App/       SwiftUI screens, @MainActor UI state, Apple platform adapters
Sources/Core/      pure domain operations and actor-isolated SQLite storage
Tests/             deterministic isolated core tests
Config/            machine-readable name/version/build
Assets.xcassets/   app icon and other static assets
.github/workflows/ CI, manual IPA package and automatic release
```

### Guidelines

1. Views never execute raw SQLite statements or read arbitrary unrelated app data. Use view models and explicitly defined services.
2. Core algorithms should avoid UIKit/SwiftUI for portable unit testing.
3. DB changes require explicit migrations, tests, and a backwards-compatible backup strategy. Parameterize all query values.
4. User text/audio is private. No automatic logging, analytics, plaintext secrets or network transfer by default.
5. Every UI state includes empty, error, loading and success variants. Tap targets >=44 pt, Dynamic Type, VoiceOver labels, support light/dark.
6. Keep LiveContainer permissions assumptions minimal: no global clipboard interception, no guaranteed background jobs, no arbitrary audio capture from other apps.
7. Prefer Apple frameworks before third-party libraries; review licenses and model sizes.
8. Avoid force unwrap on imported or untrusted content; bound processing time/size, support cancellation.
9. Check iOS 27 SDK compatibility and runtime on device for platform APIs rather than treating a Linux parser or source test as proof.

## Local data lifecycle

SQLite schema version 1 adds `media_trash` and `transcription_checkpoints` without rewriting existing media or segments. The migration is transactional and additive: a v0 database upgrades in place, and older builds can still read the original tables. Before manually downgrading, export important transcripts; older builds do not understand trash or pending checkpoints. Media metadata uses an UPSERT to preserve child transcripts. Subtitle replacement and checkpoint removal commit in the same transaction, so a failed replacement restores the previous transcript and pending job.

Speech checkpoints store the selected language, next chunk offset and completed phrases independently of the published transcript. Importing subtitles clears the pending job; speech publishes its staged phrases only after successful completion. The immutable local media copy is the checkpoint's source. Moving a recording to trash hides it from library/search but keeps the file, transcript and checkpoint until explicit permanent deletion. Search normalizes Unicode in SQLite using the same rule as the in-recording filter, while binding and escaping the query literally.

`MediaFileImport` performs bounded stream copies and subtitle parsing away from the main actor. `MediaViewModel` permits one import/transcription operation at a time and cancels it on background entry. Apple recognition retains its task, serializes completion on the main actor, and has cancellation and a 90-second per-chunk response timeout. `MediaPlayback` owns the player/time observer and saves position per recording.

Schema v2 adds `bookmarks`, `playback` and `transcription_failures`, each referencing media with cascading permanent deletion. Before upgrading an existing v0/v1 database, the SQLite Backup API creates a consistent snapshot including committed WAL data; each migration is transactional. Newer schema versions are rejected before changing the database. Existing transcript/checkpoint tables are preserved. Bookmark notes are bounded at the domain boundary and SQL values are bound parameters. The overview aggregates segment counts, pending checkpoints, failures and playback in one query. Active operations are transient UI state; paused/ready/error states derive from persisted facts.

Playback snapshots have a position and timestamp; stale asynchronous writes cannot replace newer snapshots. Legacy UserDefaults positions migrate once after a successful database write. The player saves only after playback activity, flushes on pause/background/close, ignores callbacks from obsolete player sessions, and removes periodic, KVO and end-of-playback observations when closed. The continue list excludes trash and completed recordings. Bookmark timestamps are independent of transcript segment IDs, so replacing a transcript does not invalidate saved moments. Undo restores the most recently deleted bookmark during the current app session.

The UI follows Apple's [progress guidance](https://developer.apple.com/design/human-interface-guidelines/progress-indicators): preparation uses an indeterminate indicator and measured progress uses a bar. Statuses include text and symbols alongside color. AVPlayer time observations are paired with [removal](https://developer.apple.com/documentation/avfoundation/avplayer/addperiodictimeobserver(forinterval:queue:using:)); database migration backups use the [SQLite Backup API](https://www.sqlite.org/backup.html).

## Speech readiness and recovery

`SpeechReadiness` selects a local engine from system capability facts, without assuming support for a language from its name. On iOS 26+, installed SpeechTranscriber models take priority, then installed DictationTranscriber models; legacy SFSpeechRecognizer requires on-device capability, availability and authorization. Each analyzer module checks its own supported locale and AssetInventory status independently: SpeechTranscriber hardware/language rejection must not suppress DictationTranscriber. The [legacy permission](https://developer.apple.com/documentation/speech/asking-permission-to-use-speech-recognition) does not apply to either analyzer module. Read-only checks are independent of permission prompts and model installation. View-model generations reject stale results after language changes. The system-managed [AssetInventory](https://developer.apple.com/documentation/speech/assetinventory) only receives an installation request after explicit user action; the selected module is named in the UI, download progress is observed and unregistered, and iOS may retry downloads later. Apple [recommends DictationTranscriber](https://developer.apple.com/videos/play/wwdc2025/277/) for languages/devices outside SpeechTranscriber support, without relying on users enabling Siri for that language.

Both adapters use the same audio-export/checkpoint loop. It validates loaded media duration, audio tracks, saved offsets and result timestamps; bounds temporary audio to 45 seconds and checks available disk space. Only finalized results enter checkpoints. SpeechAnalyzer input and result consumption run concurrently; finalization ends its streams, and timeout/cancellation finishes the analyzer. The legacy adapter keeps `requiresOnDeviceRecognition=true`. Failed or cancelled chunks never replace the published transcript, temporary files are removed, and old checkpoints remain compatible without a schema change. Native integration tests use real AVFoundation exports and SQLite persistence with a scripted recognizer at the speech boundary; actual speech models, permission prompts and LiveContainer still need physical-device verification.

Both analyzer module result streams use one collector, prefer attributed word timing and fall back to the module's final phrase range. Empty and volatile results do not enter checkpoints; invalid ranges fail explicitly. Native tests attach only system capability facts (supported/installed dictation locales and Russian model status), never user media or transcript text. Simulator capability metadata is not evidence of real iPhone recognition quality or guest compatibility.

## Search and text changes

Library search uses a parameterized union over media titles, transcript segments and bookmark notes, filters trash and media kind, and orders by stable media/match keys before LIMIT/OFFSET. The view model resets pagination on query/filter changes and rejects stale asynchronous results; the UI debounces typing and requests 50 matches at a time. The original transcript-only repository API delegates to the same query. Highlight ranges use the same case/diacritic-insensitive matching policy. A 10000-segment synthetic fixture checks the existing substring implementation before introducing FTS or changing its semantics.

Transcript corrections and pairwise merges use the existing replacement transaction, with an expected-content check inside BEGIN IMMEDIATE. This prevents stale editors and undo from overwriting newer text, including writes from another database connection. Editing preserves IDs/timecodes; merges keep the first ID and cover both time ranges. UI editing holds the existing operation lock and explicitly confirms discarding pending recognition. A single in-memory undo snapshot restores text only if the expected revised content still matches; it never resurrects discarded checkpoints. Notes export uses the same time formatter as playback. These features require no schema upgrade.

## Data safety and summaries

Schema v3 adds one saved summary per recording with its source transcript snapshot. SQLite Backup API preserves committed WAL data before migration. Summary drafts select up to twelve evenly distributed fragments, carry original timecodes, and never call a remote model. Editing the transcript retains summaries; comparing the saved source with current segments identifies outdated drafts. Summary replacement is explicit and exports remain local.

Full backups are folders exported through UIDocumentPicker. A serialized backup service uses a consistent SQLite snapshot and copies every referenced immutable media file, including trash, with bounded buffers, size checks, disk-space checks and SHA-256. A manifest is written only after all files succeed. Restore accepts only empty libraries, stages files in a private temporary directory, rejects traversal, symlinks, duplicates, unsupported formats and mismatched file sets/hashes, then checks SQLite integrity and foreign keys. Files are installed before the final SQLite Backup API transaction; errors remove only files installed by this attempt. The staged connection is snapshotted again before restore so migrations cannot leave data only in WAL. Backups are unencrypted and must be saved outside the guest container to survive its removal. Native integration tests exercise complete copies, corruption, unsafe paths and nonempty-library protection; real Files providers require device verification.

## Continuous delivery contract

- Work on `feature/*` / `fix/*`. AI coding agent creates commits only when it has actual working tree and Git permissions; never hallucinate commits or GitHub releases.
- `feat:` -> SemVer minor; `fix:` / `perf:` -> patch; `!` or `BREAKING CHANGE:` -> major; non-release types do not bump.
- An explicit `Config/release.json` beta policy pins the numeric bundle version and sequences `v1.0.0-beta.N` prerelease tags; build numbers still increase. The planner uses the most recent reachable release tag so old feature commits do not cause repeated releases. Stable releases resume when that policy is deliberately removed.
- CI runs core tests plus unsigned arm64 iOS build for changes; developers must not declare a build successful unless the Actions job passed.
- After a `feat`/`fix` lands on `master`, `auto-release.yml` creates a versioned release branch, bumps version/build and changelog, runs tests, builds IPA, checks Mach-O ARM64, publishes GitHub Release, fast-forwards into master, then deletes release branch.
- Protected branch cannot be force-pushed or bypassed; fallback opens PR, which may require approval. Token policy, GitHub Actions permissions, quota and repo settings must be configured by owner.
- A repository's `GITHUB_TOKEN` pushes generally don't trigger other push workflows. The release workflow therefore explicitly performs tests/build/publish, without relying on a chain triggered by its own commits.
- No secret keys or credentials committed. For personal unsigned IPA the project uses `CODE_SIGNING_ALLOWED=NO`; LiveContainer signing is done independently.

## Definition of done

- Behaviour and edge cases covered by core tests.
- Release scripts and generated Xcode project deterministic.
- All GitHub workflows pass on cloud Xcode; IPA uploaded and passes `verify_ipa.py`.
- Smoke test on iPhone in LiveContainer: import, launch, permissions, main operations, relaunch with persistent data, app switch, interruption, database recoverability.
- Update `CHANGELOG` via automated release and keep docs in sync with actually implemented functions.
